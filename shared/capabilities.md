# Capabilities

A capability is a part of the system's behavior, as its users or operators observe it, that lasts and can be accepted on its own: a user-facing feature (`file-transfer`), an internal capability or shared foundation (`peer-connection`), or a quality requirement that spans many parts (`graceful-shutdown`, `diagnostic-logging`). Each capability has one directory directly in `docs/specs/`, however many capabilities there are.

- **Split by behavior.** A capability is bounded by its behavior, whichever processes or modules carry it out: how they share the work belongs in its design, and the code follows the modules of the architecture (`arch/architecture.md`), so a capability's code may be spread across several of them.
- **Split by what changes together.** A part with its own purpose and scenarios, that will gain requirements on its own, and that can be accepted on its own, is a capability of its own, so that a later request reopens only the part it changes, and work on unrelated parts is not held in one change. Parts that always change together are one capability.
- **One owner.** Each requirement and each shared interface belongs to exactly one capability; others refer to it. An end-to-end flow belongs to the capability that is its goal, which depends on the others; a flow that is a product concept of its own is a capability.
- **Built in order.** Most capabilities are built on others, and that is expected; the dependencies only go one way, so that the capabilities can be put in an order in which each is built on those before it, and can be accepted with only them (`shared/conventions.md`). When two capabilities would need each other, one of them usually holds a step that belongs to the other, such as an authorization that also states what happens once it succeeds: move the step to the capability whose behavior it is, and the dependency runs one way. Merge them only when they cannot be built or accepted apart, and always change together.
- **Change in place.** New behavior, changed rules, and bug fixes for an existing part belong to that capability; a request creates a new capability only for a new part, by the same measure as the split.
- **No directory for work that does not change behavior.** Refactoring, dependency upgrades, build migrations, and cleanups get none: project rules they settle go to steering, and design changes go to the affected capability's design.md. If such work leaves an outcome that can be verified (for example, "the project builds with one command on a clean machine"), that outcome is a technical capability.
- **Names** are 2–3 lowercase English words joined by hyphens: what the capability acts on, then what it does, the action written as a noun, such as `file-transfer`, `clipboard-sync`, or `message-search`. A lone noun such as `account` or `calendar` names everything about a thing, and draws in every later request about it; the action keeps the capability to its behavior. A feature that the product itself names, and its users know by that name, keeps that name when it stands for one behavior, such as `privacy-screen`. Each word has a clear meaning: a word whose meaning is vague, such as `management`, says nothing of the behavior, and is never used, not even when the product's own name for the feature has it; a capability that no clear action fits usually holds several parts, and is split by what changes together. The action is the behavior of the capability, never the work of a change (`file-transfer`, not `add-resume-upload`), and names have no versions or dates. A name tells a reader who knows the product, but not its requirements, which part it is, and sets it apart from the other capabilities: a word that could mean several parts is qualified by what it applies to, such as `session-recording` rather than `recording`. Names are unique across the project, and the directory name is the capability's name.
- **Restructuring.** Splitting, merging, renaming, or deleting a capability updates every reference to it in the documents at once, such as the dependencies of other capabilities. Once it has code, restructuring is a requirement change of each capability that holds its criteria afterwards (`shared/phases.md`), and the code, tests included, follows when that change is implemented (`shared/conventions.md`).
