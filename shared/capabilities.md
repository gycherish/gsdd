# Capabilities

A capability is a part of the system that lasts, has its own behavior, and can be accepted on its own: a user-facing feature (`file-transfer`), an internal capability or shared foundation (`peer-connection`, `wire-protocol`), or a quality requirement that spans many parts (`graceful-shutdown`, `diagnostic-logging`). Each capability has one directory directly in `docs/specs/`, however many capabilities there are.

- **Split by behavior, not by code structure.** A capability may span several processes or modules; how they share the work belongs in its design. Do not create capabilities per process, module, layer, or pipeline stage. Nor is the code organized by capability: it follows the modules of the architecture (`arch/architecture.md`), and a capability's code may be spread across several of them.
- **One owner.** Each requirement and each shared interface belongs to exactly one capability; others refer to it. An end-to-end flow belongs to the capability that is its goal, which depends on the others; a flow that is a product concept of its own is a capability.
- **Change in place.** New behavior, changed rules, and bug fixes for an existing part belong to that capability. Create a new capability only for a new part: one with its own purpose and scenarios, that will gain requirements on its own, and that can be accepted on its own.
- **No directory for work that does not change behavior.** Refactoring, dependency upgrades, build migrations, and cleanups get none: project rules they settle go to steering, and design changes go to the affected capability's design.md. If such work leaves an outcome that can be verified (for example, "the project builds with one command on a clean machine"), that outcome is a technical capability.
- **Names** are 1–3 lowercase English words joined by hyphens, naming the part, never the activity (`file-transfer`, not `add-resume-upload`), with no versions or dates. A name tells a reader who knows the product, but not its requirements, which part it is, and sets it apart from the other capabilities: a word that could mean several parts is qualified by what it applies to, such as `session-recording` rather than `recording`, or `clipboard-sync` rather than `clipboard`. Names are unique across the project, and the directory name is the capability's name.
- **Restructuring.** Splitting, merging, renaming, or deleting a capability updates every reference to it in the documents at once, such as the dependencies of other capabilities. Once it has code, restructuring is a requirement change of each capability that holds its criteria afterwards (`shared/phases.md`), and the code, tests included, follows when that change is implemented (`shared/conventions.md`).
